========================================================
FITUR WIRABUMI - DOKUMENTASI LENGKAP DAN JUJUR
(ditulis ulang dari nol, langsung dari kode yang berjalan saat ini)
========================================================

Dokumen ini menjelaskan SEMUA fitur WIRABUMI apa adanya: mana yang
benar-benar dihitung/tersimpan dari data asli, mana yang masih
berbasis aturan, dan mana yang sekarang benar-benar memakai AI (LLM
Groq di 4 titik, plus OCR Tesseract.js). Tidak ada yang dilebih-
lebihkan, tidak ada yang disembunyikan.

TENTANG WIRABUMI
--------------------------------------------------------
WIRABUMI adalah aplikasi pembukuan dan kesiapan pengajuan KUR (Kredit
Usaha Rakyat) untuk pelaku UMKM di kawasan Solo Raya. Nama WIRABUMI
sendiri singkatan dari "Wirausaha Bumi Solo Raya" - "Wira" dari kata
wirausaha, "Bumi" merujuk pada wilayah/tanah Solo Raya (cerita lengkap
ada di halaman Tentang di dalam aplikasi).

Aplikasi ini FUNGSIONAL NYATA: database sungguhan, akun pengguna
sungguhan, dan seluruh perhitungan (skor, plafon, laba rugi) benar-benar
jalan dari data yang kamu catat sendiri - BUKAN tampilan/mockup statis.


========================================================
ARSITEKTUR & STACK TEKNIS
========================================================
- Frontend: React 19 + Vite (client-side routing pakai react-router-dom
  v7). Semua halaman ada di src/pages/, komponen bersama (navbar,
  dashboard usaha) di src/components/.
- Backend: Node.js + Express 5, di server/. Setiap grup fitur punya
  file route sendiri di server/routes/ (auth, profile, transactions,
  expenses, report, score, kur, chat, feedback, notifications, quests,
  public).
- Database: PostgreSQL yang jalan LOKAL di komputer sendiri (bukan
  Supabase, bukan cloud database apa pun). Skema lengkap ada di
  server/schema.sql, termasuk 2 fungsi SQL inti (compute_score dan
  get_kur_offer) yang jadi satu-satunya sumber kebenaran skor & plafon
  - dipanggil dari banyak tempat (halaman Skor, halaman KUR, chatbot,
  sistem quest, dashboard Dinkop) supaya angkanya selalu konsisten,
  tidak dihitung ulang dengan rumus berbeda-beda di tiap halaman.
- Autentikasi: token JWT (jsonwebtoken), kata sandi di-hash dengan
  bcryptjs. Middleware requireAuth mewajibkan token valid dan
  menyaring semua query database berdasar user_id - isolasi data antar
  akun dijamin di server, bukan cuma disembunyikan di tampilan.
- Upload file: multer, dipakai untuk foto profil (avatar) dan foto
  bukti transfer (dibaca di browser, tidak diunggah ke server untuk
  di-OCR - lihat bagian Pembukuan).
- PDF: jsPDF + jspdf-autotable, dipakai untuk berkas KUR dan Laporan
  Laba Rugi.
- OCR: Tesseract.js, dipakai saat unggah foto bukti transfer - lihat
  penjelasan detail di bagian "APAKAH ADA YANG BENERAN AI" di bawah.
- LLM: server/lib/groqClient.js adalah modul bersama untuk memanggil
  Groq API (model llama-3.3-70b-versatile), dipakai di 4 titik (parser
  Tempel Chat, narasi Skor, parser hasil OCR foto, Mas Sido - lihat
  bagian "APAKAH ADA YANG BENERAN AI" untuk detail lengkapnya). Timeout
  8 detik per panggilan, dan KEEMPATNYA otomatis jatuh ke logic
  rule-based lama kalau panggilan Groq gagal/timeout/API key kosong -
  tidak ada fitur yang bisa mati total hanya karena Groq bermasalah.
- Database & autentikasi tetap 100% lokal (Postgres sendiri, bukan
  Supabase). Satu-satunya panggilan ke layanan pihak ketiga di luar
  komputer sendiri adalah ke Groq API untuk 3 fitur LLM di atas -
  dan itu pun opsional (lihat GROQ_API_KEY di .env.example): kalau
  kosong, aplikasi tetap jalan penuh lewat fallback rule-based, cuma
  tanpa bagian yang benar-benar AI. Frontend di http://localhost:5173
  (Vite dev server), backend di http://localhost:4001 (Express),
  database di localhost:5432 (Postgres).


========================================================
PANDUAN MENJALANKAN (SETUP LOKAL)
========================================================
Prasyarat:
- Node.js 18 ke atas (dicoba dengan v24.12.0). Versi 18+ WAJIB karena
  fitur AI (server/lib/groqClient.js) memakai fetch/AbortController
  bawaan Node, bukan library tambahan.
- PostgreSQL sudah terpasang & service-nya jalan di komputer sendiri.
- (Opsional) API key Groq gratis, kalau mau 3 fitur AI benar-benar
  aktif memanggil LLM, bukan cuma jalan di mode cadangan.

Langkah-langkah:

1. Install dependency (satu kali saja - backend & frontend jadi satu
   package.json di root project, tidak ada folder server/node_modules
   terpisah):
     npm install

2. Siapkan database PostgreSQL. Lewat psql atau GUI (mis. pgAdmin),
   buat role & database-nya dulu:
     CREATE ROLE wirabumi_app WITH LOGIN PASSWORD 'ganti_password_ini';
     CREATE DATABASE wirabumi OWNER wirabumi_app;
   Lalu jalankan SELURUH isi server/schema.sql ke database wirabumi itu
   (membuat semua tabel + fungsi compute_score/get_kur_offer/dst):
     psql -U wirabumi_app -d wirabumi -f server/schema.sql
   Kalau muncul error "function gen_random_uuid() does not exist"
   (biasanya cuma di Postgres versi lama, di bawah 13), jalankan dulu
   satu baris ini sebelum mengulang perintah di atas:
     CREATE EXTENSION IF NOT EXISTS pgcrypto;

3. Salin .env.example jadi .env di root project, lalu isi:
   - DATABASE_URL: ganti CHANGE_ME dengan password dari langkah 2.
   - JWT_SECRET: isi string acak apa saja (bebas, asal tidak kosong).
   - PORT: biarkan 4001 (harus sama dengan proxy target di
     vite.config.js - kalau diganti, ganti juga di sana).
   - GROQ_API_KEY: opsional, boleh dikosongkan dulu - aplikasi tetap
     jalan penuh lewat mode cadangan tanpa ini. Isi belakangan kalau
     mau 3 fitur AI-nya benar-benar aktif (lihat "APAKAH ADA YANG
     BENERAN AI" di bawah untuk detail masing-masing fitur).

4. Jalankan backend (satu terminal, biarkan tetap terbuka/jalan):
     npm run server
   Berhasil kalau muncul "WIRABUMI API listening on
   http://localhost:4001".

5. Jalankan frontend (terminal KEDUA yang terpisah, juga dibiarkan
   tetap jalan):
     npm run dev
   Vite akan menampilkan alamat lokalnya (biasanya
   http://localhost:5173) - buka alamat itu di browser.

6. Di browser, klik "Daftar Gratis" untuk membuat akun pertama, lalu
   mulai pakai aplikasinya (isi Pembukuan, cek halaman Skor, dst).

CARA LEBIH CEPAT (setelah setup pertama di atas selesai sekali): dobel
klik start.bat di folder utama proyek. Ini membuka terminal interaktif
(wirabumi-launcher.ps1) dengan menu navigasi panah atas/bawah - pilih
"Nyalakan Website Wirabumi" untuk menyalakan backend+frontend otomatis
(skip kalau portnya sudah kepakai/sudah nyala), tunggu sampai keduanya
benar-benar bisa diakses, lalu link lokal muncul dan otomatis kebuka di
browser. Pilih "Matikan Website Wirabumi" untuk mematikan proses backend
+ frontend dengan rapi (berdasar port, bukan asal taskkill semua node),
atau "Keluar" untuk menutup terminalnya saja tanpa mematikan apa pun.
Log proses tersimpan di folder .wirabumi-run/ (di-gitignore, bukan
bagian dari kode aplikasi). start.bat ini murni alat menjalankan lokal
untuk memudahkan - bukan pengganti langkah 1-5 di atas untuk instalasi
pertama kali.

Mengaktifkan 3 fitur AI (opsional, bisa menyusul kapan saja):
   a. Ambil API key gratis di https://console.groq.com/keys
   b. Isi GROQ_API_KEY=key_kamu di .env
   c. Matikan proses backend lalu jalankan ulang npm run server -
      WAJIB restart, karena dotenv cuma dibaca sekali saat proses
      backend baru mulai. Frontend (npm run dev) tidak perlu direstart.
   d. Coba fitur Tempel Chat / halaman Skor / unggah foto bukti
      transfer - badge "✨ Diproses AI (Groq)" akan muncul di tabel
      review kalau panggilan ke Groq berhasil. Kalau masih muncul
      "⚙️ Mode cadangan (aturan)", cek log terminal backend - akan ada
      baris yang menjelaskan kenapa (mis. key salah, API timeout).

========================================================
3. DAFTAR & MASUK (Registrasi & Login)
========================================================
- Akun sungguhan: email + kata sandi (hash bcrypt, bukan disimpan
  polos). Login mengembalikan JWT yang dipakai untuk semua request
  berikutnya.
- Setiap akun punya data pembukuan sendiri-sendiri, dijamin lewat
  requireAuth + filter user_id di setiap query - bukan cuma
  disembunyikan di tampilan.
- Tidak ada verifikasi email/OTP - begitu daftar, langsung bisa
  dipakai. Ini disengaja untuk kemudahan lokal, BUKAN standar
  keamanan aplikasi publik/produksi.
- LUPA KATA SANDI (reset password) - sekarang ADA, lewat 2 pertanyaan
  keamanan (bukan email/OTP, karena belum ada penyedia email/SMS yang
  disambungkan). Saat daftar, pengguna WAJIB mengisi jawaban "makanan
  favorit" dan "band/musisi favorit" selain email & kata sandi.
  Jawaban itu di-hash dengan bcrypt persis seperti kata sandi (tidak
  disimpan polos), dan dicocokkan tanpa peduli huruf besar/kecil atau
  spasi berlebih (jadi "Nasi Goreng" saat daftar tetap cocok dengan
  "nasi goreng" saat reset).
  Alur reset: buka halaman "Lupa kata sandi?" di halaman Masuk → isi
  email + kedua jawaban + kata sandi baru dalam SATU form → kalau
  email & kedua jawaban cocok, kata sandi langsung diganti (satu
  langkah, tidak ada token/link email terpisah). Kalau salah satu
  tidak cocok (email tidak terdaftar ATAU salah satu jawaban salah),
  pesan errornya SENGAJA generik ("Email atau jawaban tidak cocok")
  supaya tidak membocorkan mana yang sebenarnya salah atau apakah
  emailnya terdaftar.
  KETERBATASAN JUJUR: akun yang didaftarkan SEBELUM fitur ini ada
  tidak punya jawaban keamanan tersimpan (kolomnya kosong), jadi akun
  lama tidak bisa pakai reset ini sampai datanya diisi ulang secara
  manual di database - ini bukan celah keamanan, hanya konsekuensi
  wajar dari menambahkan fitur baru ke data yang sudah ada.

========================================================
5. PEMBUKUAN (Pemasukan/Penjualan)
========================================================
Halaman Pembukuan sendiri adalah tabel pencarian & pengurutan
transaksi yang sudah tersimpan (bisa cari & sortir kolom). Menambah
transaksi baru dilakukan di halaman terpisah, Pembukuan > Tambah, lewat
tiga cara:

A. INPUT MANUAL
   - Form isi tanggal, nama produk, jumlah, satuan (ada saran satuan
     umum: pcs, buah, kg, dll), harga, nama pelanggan (opsional),
     status bayar (Lunas/DP 50%/Belum Lunas).
   - Tersimpan sungguhan ke database, bisa dihapus kapan saja.

B. TEMPEL CHAT
   - Tempel isi obrolan WhatsApp/caption Instagram, sistem MENCOBA
     menebak produk, jumlah, dan harga dari teks itu.
   - SEKARANG BENERAN AI (LLM), DENGAN FALLBACK: teks chat dikirim ke
     backend (POST /api/parse/chat), yang mencoba Groq LLM
     (llama-3.3-70b-versatile, lewat server/lib/llmChatParser.js) lebih
     dulu untuk membaca chat informal (singkatan, typo, banyak transaksi
     sekaligus) dan mengekstrak semua transaksinya sebagai JSON. Kalau
     panggilan Groq gagal/timeout/API key kosong, backend OTOMATIS jatuh
     ke parser aturan (regex) lama di src/lib/chatParser.js - jadi fitur
     ini tidak akan pernah benar-benar mati hanya karena Groq bermasalah.
   - Hasil parse (dari LLM maupun fallback) SELALU tampil dulu di tabel
     review yang bisa dikoreksi (produk/jumlah/harga/status/pelanggan)
     sebelum disimpan. Tidak ada yang tersimpan otomatis tanpa dilihat
     dulu - ini berlaku sama untuk kedua jalur.
   - Ada badge kecil di atas tabel review yang menunjukkan jalur mana
     yang dipakai: "✨ Diproses AI (Groq)" atau "⚙️ Mode cadangan
     (aturan)" - supaya jujur ke pengguna jalur mana yang sebenarnya
     memproses chat itu.
   - Label "yakin" (low/medium/high): kalau lewat LLM, model diminta
     menilai sendiri seberapa lengkap info yang dia baca (qty & harga
     jelas = high, sebagian ditebak = medium/low); kalau lewat fallback
     regex, dihitung dari aturan sederhana seperti sebelumnya (apakah
     harga & jumlah sama-sama ketemu). Bukan angka yang dijamin
     100% akurat di kedua jalur - tetap perlu dicek di tabel review.

C. UNGGAH FOTO BUKTI TRANSFER
   - Unggah foto/screenshot konfirmasi transfer bank (mis. layar
     "m-Transfer: BERHASIL"), sistem mencoba membaca nominal, tanggal,
     dan keterangannya.
   - DUA TAHAP (tahap 1 TIDAK diubah sama sekali oleh penambahan LLM):
     1) OCR (pengenalan teks dari gambar) memakai Tesseract.js - teknologi
        AI sungguhan (lihat penjelasan di bawah), berjalan 100% di
        browser sendiri; foto TIDAK pernah dikirim ke server WIRABUMI
        atau cloud manapun. Model bahasa Indonesia untuk OCR (~10-20MB)
        diunduh dari CDN publik saat dipakai pertama kali, lalu
        tersimpan cache browser.
     2) Teks mentah hasil OCR itu (bukan fotonya) dikirim ke backend
        (POST /api/parse/receipt), yang mencoba Groq LLM lebih dulu
        (server/lib/llmReceiptParser.js) untuk membaca teks OCR yang
        sering berantakan/typo dan mengekstraknya jadi data terstruktur
        (nominal, tanggal, bank, nama penerima, berita, dst) - LLM jauh
        lebih toleran terhadap noise OCR dibanding regex kaku. Kalau
        Groq gagal/timeout/API key kosong, backend OTOMATIS jatuh ke
        parser aturan (regex) lama di src/lib/receiptParser.js.
   - Sama seperti Tempel Chat, ada badge "✨ Diproses AI (Groq)" atau
     "⚙️ Mode cadangan (aturan)" di atas tabel review, dan hasil dari
     jalur manapun tetap harus melalui tabel review sebelum disimpan.
   - Hasil OCR mentah bisa dilihat lewat tombol "Lihat teks hasil OCR"
     untuk verifikasi manual. Hasil ekstraksi tetap masuk tabel review
     yang bisa dikoreksi sebelum disimpan.
   - ASUMSI PENTING: fitur ini dirancang untuk transfer MASUK
     (pelanggan bayar ke usahamu). Belum membedakan transfer masuk vs
     keluar - semua yang diunggah dicatat sebagai transaksi penjualan.
     Kalau fotonya sebenarnya transfer keluar (belanja/bayar orang
     lain), jangan disimpan sebagai penjualan.

========================================================
7. LAPORAN LABA RUGI
========================================================
- Pendapatan (dari Pembukuan) dikurangi Beban (dari Pengeluaran,
  dikelompokkan per kategori) untuk periode satu bulan yang dipilih =
  Laba/Rugi Bersih. SEMUA ANGKA DIHITUNG REAL dari query SQL langsung
  ke tabel transactions & expenses.
- Bisa diunduh sebagai PDF dengan struktur Laporan Laba Rugi standar
  SAK EMKM (Standar Akuntansi Keuangan untuk UMKM): bagian Pendapatan,
  Beban Usaha per kategori, lalu Laba/Rugi Bersih.
- KETERBATASAN JUJUR: ini BUKAN laporan keuangan SAK EMKM yang
  lengkap. SAK EMKM formal punya 3 laporan (Laba Rugi, Posisi
  Keuangan/Neraca, Catatan atas Laporan Keuangan) - WIRABUMI baru
  menyediakan yang pertama, karena baru itu yang bisa dihitung dari
  data yang dicatat sekarang (penjualan + pengeluaran). Laporan Posisi
  Keuangan butuh pencatatan aset/utang/modal yang belum ada fiturnya.
  Laporan ini juga tidak melalui jurnal umum/buku besar debit-kredit
  formal - dihitung langsung dari penjumlahan SQL. Untuk kebutuhan
  resmi (pajak, audit), tetap konsultasikan ke akuntan/konsultan pajak.

ESTIMASI KEWAJIBAN PAJAK (PPh Final UMKM) - kartu tambahan di halaman
yang sama, di bawah Ringkasan Laba Rugi:
- MURNI SQL/MATEMATIKA seperti Skor & KUR - TIDAK melibatkan LLM sama
  sekali, dan TIDAK memengaruhi compute_score()/get_kur_offer(). Dasar
  hukum: skema PPh Final UMKM 0,5% dari omzet bruto (PP 55/2022 jo.
  PP 20/2026), dihitung oleh fungsi SQL compute_tax_estimate().
- Bergantung pada "Kategori Wajib Pajak" yang diisi di Profil Usaha
  (Orang Pribadi/default, atau Badan Usaha). HANYA Orang Pribadi yang
  dapat ambang bebas pajak Rp500 juta/tahun pajak - Badan Usaha kena
  0,5% sejak rupiah pertama, tanpa ambang.
- PERHITUNGAN MARGINAL: kalau omzet kumulatif tahun berjalan baru
  melewati Rp500 juta di TENGAH bulan, hanya bagian yang melebihi
  Rp500 juta itu yang kena pajak bulan tersebut - bukan seluruh omzet
  bulan itu, apalagi omzet setahun penuh.
- 4 status (badge warna): "Di bawah ambang bebas pajak" (hijau, hanya
  Orang Pribadi di bawah Rp500jt), "Kena PPh Final 0,5%" (biru, kondisi
  normal), "Mendekati batas Rp4,8 miliar" (kuning, begitu omzet
  kumulatif tahun berjalan lewat 80% dari Rp4,8 miliar), "Melebihi
  batas Rp4,8 miliar" (merah - di luar skema ini, disarankan konsultasi
  ke konsultan pajak; WIRABUMI tidak menghitung pajak normal Pasal 17).
- Muncul juga sebagai section tambahan di PDF Laporan Laba Rugi, dan
  sebagai satu baris "sinyal kepatuhan pajak tambahan" (bukan kewajiban
  terpisah) di PDF Berkas KUR - keduanya memakai compute_tax_estimate()
  yang sama, tidak dihitung ulang dengan logic berbeda.
- KETERBATASAN JUJUR (WAJIB dibaca sebelum dipakai serius): ini murni
  ESTIMASI dari data pembukuan sendiri, bukan perhitungan resmi. Tidak
  melacak masa berlaku 7 tahun skema PPh Final untuk Orang Pribadi
  (asumsi masih berlaku). Tidak mengganti lapor pajak/SPT/Coretax sama
  sekali - disclaimer ini selalu tampil di kartu maupun di PDF. Untuk
  kewajiban pajak resmi, tetap konsultasikan ke akuntan/konsultan pajak
  terdaftar atau cek pajak.go.id / Coretax.


========================================================
8. SKOR KELAYAKAN
========================================================
Skor 0-100, DIHITUNG SUNGGUHAN oleh fungsi SQL compute_score() -
bukan angka acak/hardcode, dipanggil ulang otomatis tiap kali data
transaksi/legalitas berubah. Rumus (bobot sama rata, 25% masing-masing):

1. Konsistensi transaksi harian - jumlah HARI BERBEDA ada transaksi
   dalam 90 hari terakhir, dibagi 30 hari, dikali 100 (maks. 100).
2. Volume penjualan bulanan - bandingkan total omzet 30 hari terakhir
   vs 30 hari sebelumnya. Kalau periode sebelumnya nol tapi sekarang
   ada penjualan, dianggap pertumbuhan 100%. Skor = 50 + (persentase
   pertumbuhan × 100), dibatasi 0-100.
3. Rasio pelanggan tetap - dari kolom "nama pelanggan" di transaksi
   180 hari terakhir. Kalau nama yang sama muncul >1 kali, dianggap
   pelanggan setia. Kalau transaksi berisi nama pelanggan kurang dari
   3, skor bagian ini otomatis diberi nilai netral 50 (bukan 0/100)
   supaya tidak menghukum pengguna yang jarang isi nama pelanggan.
4. Kelengkapan legalitas - dari 3 dokumen (NIB, P-IRT, Sertifikasi
   Halal) yang dicentang di halaman KUR, dibagi 3 dikali 100.

Skor >= 60 berstatus "Layak Diajukan", di bawah itu "Perlu
Peningkatan". Halaman Skor juga menampilkan tip spesifik per faktor
untuk menaikkan skor.

PENJELASAN NARATIF (LAPISAN AI TAMBAHAN, BUKAN PENGGANTI RUMUS): di
atas angka-angka hasil compute_score() di atas, halaman Skor sekarang
juga menampilkan kartu "Penjelasan Skor" - 2-3 kalimat naratif berbahasa
Indonesia santai yang dibuat oleh Groq LLM (server/lib/llmScoreNarrative.js),
mis. "Konsistensi transaksimu kuat (78/100), tapi legalitas masih jadi
titik lemah (45/100)...". PENTING: compute_score() SENDIRI TIDAK
disentuh sama sekali oleh LLM - LLM hanya diberi angka yang SUDAH
dihitung SQL dan diminta menuliskannya ulang jadi kalimat, tidak pernah
diminta menghitung atau mengarang angka baru. Kalau Groq gagal/API key
kosong, kartu ini tetap tampil dengan kalimat fallback statis sederhana
(disusun dari total_score & status asli, bukan kalimat AI) - halaman
Skor tidak akan pernah error hanya karena Groq bermasalah.

10. MAS SIDO (Chatbot Asisten Keuangan)
========================================================
Nama "Mas Sido" diambil dari kata "sido" pada motif batik Sidomukti,

WIRABUMI jadi dan tercapai. (Ini beda dengan asal nama WIRABUMI sendiri

UPDATE: SEKARANG BENERAN AI (LLM), DENGAN FALLBACK - Mas Sido tadinya
murni pencocokan kata kunci (regex), tapi sekarang jawabannya lewat
POST /api/chat-messages/ask: frontend mengirim pertanyaan + data konteks
usaha (skor & 4 faktornya, simulasi KUR, omzet bulan ini, produk
terlaris, legalitas - data yang SAMA yang sudah ditampilkan di halaman
lain, cuma dikumpulkan ulang di sini) ke backend, yang mencoba Groq LLM
lebih dulu (server/lib/llmChatbotAnswer.js) untuk menjawab pertanyaan
bebas dalam bahasa natural, BUKAN cuma pertanyaan yang persis cocok
pola regex. LLM diberi instruksi tegas: jawab HANYA dari data yang
diberikan, jangan mengarang angka, dan kalau datanya tidak cukup untuk
menjawab (termasuk pertanyaan di luar topik usaha/keuangan), jawab
jujur "tidak tahu" sambil menyarankan topik yang bisa dijawab - bukan
sok tahu menebak-nebak.
Kalau panggilan Groq gagal/timeout/API key kosong, backend OTOMATIS
jatuh ke mesin jawaban aturan (regex) lama, yang sekarang dipindah ke
src/lib/chatbotAnswer.js (logikanya PERSIS sama seperti sebelumnya,
cuma dipindah lokasi filenya supaya bisa dipakai backend sebagai
fallback juga) - jadi Mas Sido tidak akan pernah benar-benar diam
hanya karena Groq bermasalah.
JUJUR - bedanya dengan versi lama: dulu Mas Sido HANYA bisa menjawab
pertanyaan yang persis mengandung salah satu kata kunci di daftar
tetapnya; kalau tidak, selalu dijawab "belum punya jawaban pasti".
Sekarang, lewat LLM, dia bisa memahami pertanyaan yang ditulis dengan
gaya bebas/berbelit (mis. "bisnisku lagi lesu, gimana caranya biar bisa
dapet pinjaman modal dari bank?") dan tetap menjawab relevan dari data
asli - sesuatu yang mustahil dilakukan versi keyword-matching murni.
Riwayat chat tersimpan ke database, dibatasi 5 percakapan terakhir (10
pesan) - lebih dari itu, yang paling lama otomatis dihapus. Ini tidak
berubah dari sebelumnya.

17. PERAN & HAK AKSES (Role-Based Access Control)
========================================================
UPDATE BESAR: sistem peran diperluas dari 3 jadi 4 peran, dengan
dashboard yang jauh lebih kontras satu sama lain. Ada 4 peran akun:

- UMKM Owner (umkm_owner, dulu "User") - pemilik usaha, default semua
  akun baru. Hanya melihat dashboard pribadinya sendiri (bagian 13A).
- Government / Pemerintah Dinkop (government, dulu "Admin") - staf
  Dinas Koperasi. Melihat data agregat seluruh UMKM, tanpa identitas
  transaksi mentah.
- Bank (bank_officer, BARU) - mitra penyalur KUR. Hanya melihat UMKM
  yang SUDAH MEMBERI IZIN (consent) untuk dilihat profil kelayakannya.
- Super Admin (super_admin, tidak berubah) - developer/pengelola
  sistem. Melihat semuanya, plus metrik kesehatan sistem.

Setiap peran punya dashboard & menu navbar yang BENAR-BENAR berbeda,
bukan halaman yang sama dengan tombol disembunyikan - UMKM Owner cuma
melihat Dashboard/Beranda/Cara Kerja/Keuangan/Mas Sido; Government
melihat Dashboard Dinkop + menu Admin (Monitoring, Dampak); Bank cuma
melihat satu link "Dashboard" ke halamannya sendiri; Super Admin
melihat semuanya plus System.

PEMBATASAN AKSES INI NYATA, BUKAN KOSMETIK: setiap endpoint dijaga
oleh middleware requireRole di server (server/auth.js) yang mengecek
peran pengguna LANGSUNG dari database di setiap request (bukan dari
isi token JWT, supaya perubahan peran langsung berlaku, tidak perlu
tunggu token lama kedaluwarsa). Kalau peran tidak sesuai, server
membalas HTTP 403 - bisa dibuktikan langsung lewat panggilan API
manual (curl), bukan cuma "link-nya disembunyikan di tampilan".
ProtectedRoute di frontend juga mengecek peran untuk pengalaman
pengguna yang mulus (langsung tampil "Akses ditolak" tanpa perlu
menunggu API menolak), tapi pengecekan itu HANYA kosmetik/UX - kalaupun
seseorang mengakalinya di sisi frontend, permintaan ke server tetap
akan ditolak dengan 403.

MIGRASI DATA: akun lama dengan peran "user" otomatis jadi "umkm_owner",
dan "admin" otomatis jadi "government" - nilai lama di kolom
activity_log.role_at_time SENGAJA TIDAK ditulis ulang (tetap
menunjukkan "user"/"admin" apa adanya untuk baris aktivitas dari
sebelum migrasi), konsisten dengan prinsip "role_at_time dicatat saat
kejadian, tidak pernah ditulis ulang".

A. HALAMAN MONITORING AKTIVITAS (/admin/monitoring - Government & Super Admin)
   - Setiap tindakan penting (daftar, masuk, catat transaksi, catat
     pengeluaran, buat berkas KUR, ubah status legalitas, ubah peran
     pengguna, ubah izin Bank, review pengajuan KUR oleh Bank)
     TERCATAT NYATA ke tabel activity_log di database - bukan data
     contoh/statis. Kalau pencatatan aktivitas gagal karena alasan
     apapun, itu tidak pernah menggagalkan permintaan utama pengguna
     (mis. transaksi tetap tersimpan walau logging gagal).
   - "Pengguna Aktif" = jumlah akun berbeda yang punya aktivitas dalam
     24 jam terakhir. "Aktivitas Hari Ini" = jumlah baris activity_log
     sejak tengah malam. "Rincian Aktivitas Hari Ini" (BARU) memecah
     angka itu per jenis aksi (mis. "11 Masuk, 3 Update Legalitas").
     Semuanya dihitung ulang setiap halaman dibuka.
   - "Distribusi Aktivitas per Peran" = jumlah aktivitas 30 hari
     terakhir dikelompokkan per peran SAAT aktivitas itu terjadi
     (role_at_time) - kalau seseorang naik jabatan, riwayat
     aktivitasnya SEBELUM naik jabatan tetap tercatat dengan peran
     lama, tidak ditulis ulang (lihat catatan migrasi di atas).
   - "Aktivitas Terbaru" ditampilkan sebagai tabel log (waktu, pengguna,
     peran, aksi) berisi 20 aktivitas terakhir dari SELURUH pengguna,
     bukan cuma milik yang sedang login.
   - KHUSUS SUPER ADMIN (BARU) - 3 bagian tambahan yang TIDAK muncul
     untuk Government (karena membuka identitas akun staf Bank/Super
     Admin lain, bukan cuma UMKM):
     * "Pengguna Terdaftar" & "Peran Terdaftar" (kartu KPI) - jumlah
       akun asli dari tabel users, dihitung ulang tiap halaman dibuka.
     * "Distribusi Peran Pengguna Terdaftar" - jumlah AKUN per peran
       saat ini (bukan jumlah aktivitas seperti poin di atas - dua hal
       yang beda: satu akun bisa punya banyak aktivitas).
     * "Pengguna Paling Aktif (30 Hari)" - 8 akun dengan jumlah baris
       activity_log terbanyak 30 hari terakhir, diurutkan dari yang
       paling aktif, memakai peran akun SAAT INI (bukan role_at_time)

   - Mengubah peran akun lain antara UMKM/Government/Bank lewat
     dropdown, memanggil endpoint yang juga dijaga
     requireRole('super_admin') di server, bukan cuma disembunyikan di
     tampilan untuk role lain.
   - JUJUR - KETERBATASAN SENGAJA: peran "Super Admin" TIDAK BISA
     diberikan lewat halaman ini atau API manapun, hanya lewat akses
     database langsung (satu kali, saat setup awal). Ini pembatasan
     yang disengaja untuk memperkecil risiko privilege-escalation
     (kalau lewat API bisa, satu Super Admin yang disusupi bisa
     membuat Super Admin baru tanpa batas) - bukan keterbatasan teknis
     yang kelupaan.

E. SYSTEM (/admin/system - KHUSUS Super Admin) - FITUR BARU
   - Metrik NYATA (bukan angka karangan): Total Pengguna, Total UMKM,
     Ukuran Database (pg_database_size() asli), Status Database
     (cek koneksi asli lewat `select 1`).
   - "Pemakaian LLM (7 Hari Terakhir)": hitungan sukses/gagal ASLI dari
     setiap panggilan Groq (tabel llm_usage_log, ditulis dari dalam
     server/lib/groqClient.js setiap callGroq() selesai) - dipecah per
     fitur (chat_parser, score_narrative, receipt_parser, chatbot).
   - "Error Log Terbaru": error server ASLI yang tertangkap oleh
     error-handler Express global (server/index.js), ditulis ke tabel
     error_log. Kalau belum pernah ada error, kartunya kosong - bukan
     dipalsukan supaya kelihatan "ada aktivitas".
   - "Role Management": pintasan ke Kelola Pengguna. "Permission
     Management": tabel referensi statis (bukan editor dinamis) yang
     mendaftar rute mana bisa diakses peran mana - dokumentasi, bukan
     mekanisme baru.


========================================================
APAKAH ADA YANG BENERAN AI?
========================================================
Jawaban jujur (per update terbaru): YA, di 5 titik - 1 titik OCR
(Tesseract.js, sudah ada sejak awal) dan 4 titik LLM (Groq, model
llama-3.3-70b-versatile). Semua 4 titik LLM PUNYA FALLBACK otomatis ke
logic rule-based lama, jadi tidak satupun fitur berhenti total kalau
Groq lambat/down/API key belum diisi.

BUKAN AI SAMA SEKALI (murni aturan/matematika, tidak berubah):
- Skor kelayakan & simulasi KUR (compute_score/get_kur_offer) - rumus
  SQL biasa (rata-rata berbobot, tabel pengganda). SENGAJA tidak pernah
  disentuh LLM sedikit pun, supaya angka yang jadi dasar pengajuan KUR
  tetap 100% bisa diaudit/dijelaskan asal-usulnya - LLM hanya boleh
  menuliskan ULANG angka ini jadi kalimat (lihat "Narasi Skor" di
  bawah) atau menjawab pertanyaan tentangnya (lihat "Mas Sido" di
  bawah), tidak pernah menghitungnya.
- Sistem quest & lencana - katalog tetap dengan syarat deteksi
  otomatis, bukan model apa pun.

SEKARANG BENERAN AI, DENGAN FALLBACK RULE-BASED (Groq LLM,
llama-3.3-70b-versatile, lewat server/lib/groqClient.js - timeout 8
detik per panggilan):
1. Parser Tempel Chat (server/lib/llmChatParser.js, endpoint
   POST /api/parse/chat) - LLM membaca chat penjualan informal dan
   mengekstrak semua transaksi jadi JSON. Fallback: regex lama di
   src/lib/chatParser.js (src/lib/chatParser.js sendiri TIDAK dihapus,
   masih dipakai persis sebagai fallback).
2. Narasi Skor (server/lib/llmScoreNarrative.js) - LLM menulis 2-3
   kalimat penjelasan dari angka skor yang SUDAH dihitung SQL (lihat
   catatan di atas - LLM tidak pernah menghitung skornya sendiri).
   Fallback: kalimat statis sederhana yang tetap disusun dari angka
   asli (total_score & status), bukan LLM.
3. Parser hasil OCR foto (server/lib/llmReceiptParser.js, endpoint
   POST /api/parse/receipt) - Tesseract.js tetap yang membaca teks dari
   foto (tidak berubah), tapi teks mentahnya sekarang diekstrak jadi
   data terstruktur oleh LLM (lebih toleran ke noise/typo OCR
   dibanding regex kaku). Fallback: regex lama di
   src/lib/receiptParser.js (juga tidak dihapus).
4. Mas Sido, chatbot (server/lib/llmChatbotAnswer.js, endpoint
   POST /api/chat-messages/ask) - LLM menjawab pertanyaan bebas
   berbahasa natural, diberi data konteks usaha yang sama seperti versi
   lama (skor, KUR, omzet, produk terlaris, legalitas) dan diinstruksi
   tegas untuk HANYA memakai angka itu, tidak mengarang, dan jujur
   bilang "tidak tahu" kalau datanya tidak cukup. Fallback: mesin
   jawaban kata-kunci lama, dipindah ke src/lib/chatbotAnswer.js (logika
   IDENTIK dengan sebelumnya, cuma pindah lokasi file).

Di 3 titik yang menghasilkan data terstruktur (parser Tempel Chat, OCR
foto, dan - kalau kamu tambahkan tampilannya - Mas Sido), badge kecil
"✨ Diproses AI (Groq)" atau "⚙️ Mode cadangan (aturan)" bisa dipakai
untuk menunjukkan jalur mana yang sebenarnya memproses input; saat ini
badge itu sudah tampil di tabel review Tempel Chat & Unggah Foto.

Tesseract.js (OCR, dari awal sudah ada, tidak diubah):
- Mesin OCR (pengenalan karakter dari gambar) yang di dalamnya memakai
  model jaringan saraf terlatih (LSTM). Teknologi pihak ketiga yang
  sudah jadi (bukan dilatih sendiri oleh tim WIRABUMI), berjalan 100%
  di browser - foto tidak pernah dikirim ke server manapun.

CATATAN PENTING soal "tanpa cloud": sebelum perubahan ini, WIRABUMI
benar-benar tidak memanggil layanan pihak ketiga apa pun. Sekarang, 3
fitur di atas memanggil Groq API (cloud, di luar komputer sendiri) -
jadi klaim "100% lokal" itu SUDAH TIDAK SEPENUHNYA BENAR LAGI untuk 3
fitur tersebut. Yang masih 100% lokal: database, autentikasi, OCR
Tesseract, dan semua fitur rule-based lainnya. GROQ_API_KEY di .env
bersifat opsional - kalau dikosongkan, aplikasi tetap jalan penuh
lewat fallback, hanya tanpa bagian yang benar-benar AI.

Jadi kalau ditanya "ini aplikasi AI?" - jawaban akuratnya: skor, KUR,
dan quest tetap murni rule-based (sengaja, supaya bisa
dipertanggungjawabkan); 4 titik yang berhubungan dengan membaca input
tidak terstruktur (chat, hasil OCR), menjelaskan skor, dan menjawab
pertanyaan bebas (Mas Sido) sekarang benar-benar memakai LLM Groq,
dengan jaring pengaman otomatis ke logic lama kalau LLM-nya bermasalah.


========================================================
KETERBATASAN YANG PERLU DIKETAHUI
========================================================
1. Mas Sido sekarang coba LLM lebih dulu (bisa paham pertanyaan bebas/
   berbelit), tapi tetap punya fallback ke pencocokan kata kunci lama
   kalau Groq gagal - di jalur fallback itu, keterbatasan lama masih
   berlaku (tidak akan paham pertanyaan yang rumit/berbelit).
2. Parser Tempel Chat sekarang coba LLM lebih dulu, tapi tetap bisa
   salah menebak (baik lewat LLM maupun fallback regex) untuk chat
   yang sangat tidak lazim - karena itu selalu ada langkah review
   sebelum disimpan, di kedua jalur.
3. Fitur unggah foto: OCR (Tesseract) hanya membaca teks, tidak
   memahami isinya - foto buram/miring/gelap bisa gagal/salah baca.
   Tahap ekstraksi setelahnya (LLM atau fallback regex) bisa membaca
   noise OCR lebih baik dari sebelumnya, tapi tetap tidak sempurna.
   Belum bisa membedakan transfer masuk (penjualan) vs keluar
   (pengeluaran).
4. Tidak ada verifikasi legalitas ke instansi resmi (OSS/BPJPH) -
   checklist murni pencatatan internal.
5. Tidak ada pengajuan KUR sungguhan ke bank - PDF adalah bahan yang
   dibawa sendiri.
6. Aplikasi jalan LOKAL di satu komputer (Postgres lokal) - belum
   di-deploy ke internet.
7. Reset kata sandi SUDAH ada (lewat 2 pertanyaan keamanan, bukan
   email - lihat bagian "Daftar & Masuk"), tapi tetap tidak ada
   verifikasi email/OTP atau notifikasi email/WhatsApp otomatis
   (notifikasi murni in-app).
8. Suku bunga KUR (6% efektif/tahun) dan formula pengganda plafon
   adalah ASUMSI simulasi, bukan angka resmi bank/pemerintah yang
   mengikat.
9. Fitur unggah foto butuh koneksi internet sekali di awal (unduh
   model bahasa OCR ~10-20MB), setelah itu tersimpan cache browser.
10. Laporan Laba Rugi bukan laporan keuangan SAK EMKM yang lengkap
    (belum ada Neraca, belum lewat jurnal umum/buku besar). Untuk
    kebutuhan resmi tetap konsultasikan ke akuntan/konsultan pajak.
11. "Poin" di sistem quest adalah label ilustratif, bukan angka yang
    ditambahkan langsung ke skor lewat pembukuan poin terpisah.
12. 4 fitur LLM (parser Tempel Chat, narasi Skor, parser OCR foto, Mas
    Sido) butuh koneksi internet & GROQ_API_KEY yang valid di .env
    untuk benar-benar aktif memakai AI. Kalau salah satu tidak
    terpenuhi (offline, key kosong/salah, API Groq sedang down/
    timeout), keempat fitur itu otomatis jalan di "mode cadangan"
    (logic rule-based lama) tanpa error - untuk Tempel Chat & Unggah
    Foto, badge di tabel review menunjukkan mode mana yang aktif; untuk
    Mas Sido & narasi Skor, cek log terminal backend untuk memastikan
    (baris "Groq gagal..." muncul kalau sedang di mode cadangan).

  PDF Berkas KUR)
- Statistik Beranda (agregat asli, tetap publik) & Dashboard Dinkop
  (agregat asli, sekarang khusus Government/Bank/Super Admin - lihat
  bagian 13 & 17)
- Riwayat chat Mas Sido (tersimpan, dibatasi 5 percakapan)

  dampak skor/plafon pakai rumus asli, lencana tersimpan permanen)

- Halaman System khusus Super Admin - ukuran database, pemakaian LLM,
  dan error log yang semuanya NYATA (llm_usage_log, error_log), bukan
  angka karangan

HYBRID: LLM DULU, FALLBACK RULE-BASED KALAU GAGAL (baru):
- Parser Tempel Chat - Groq LLM (llama-3.3-70b-versatile) lebih dulu,
  fallback ke regex src/lib/chatParser.js
- Parser hasil OCR foto - Groq LLM lebih dulu (baca teks OCR yang
  berantakan), fallback ke regex src/lib/receiptParser.js
- Narasi Skor - Groq LLM menuliskan ulang angka skor (yang tetap

- Mas Sido (chatbot) - Groq LLM menjawab pertanyaan bebas dari data

  src/lib/chatbotAnswer.js (logika identik dengan versi lama)

AI SUNGGUHAN:
- Tesseract.js - OCR (model jaringan saraf pihak ketiga) untuk membaca

  diubah oleh pekerjaan ini).
- Groq API (llama-3.3-70b-versatile) - satu-satunya panggilan ke
  layanan cloud pihak ketiga di seluruh aplikasi, dipakai di 4 fitur
  hybrid di atas, opsional lewat GROQ_API_KEY di .env.
